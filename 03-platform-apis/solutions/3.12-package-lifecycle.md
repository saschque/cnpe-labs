# Solution 3.12 – Package lifecycle

```bash
# 1. Revisions and the active revision
kubectl get functionrevisions
# NAME                                        HEALTHY   REVISION   IMAGE                                       STATE    ...
# function-patch-and-transform-abc123         True      1          xpkg.../function-patch-and-transform:v0.8.2  Active

# 2. Manual activation
kubectl patch function function-patch-and-transform --type=merge \
  -p '{"spec":{"revisionActivationPolicy":"Manual"}}'

# 3. A different version (available tags: the project's GitHub releases)
kubectl patch function function-patch-and-transform --type=merge \
  -p '{"spec":{"package":"xpkg.crossplane.io/crossplane-contrib/function-patch-and-transform:<other-version>"}}'
kubectl get functionrevisions          # new revision 2 → STATE Inactive, revision 1 stays Active

# 4. Activate the new revision
NEW=$(kubectl get functionrevisions --sort-by=.spec.revision -o name | tail -1)
kubectl patch "$NEW" --type=merge -p '{"spec":{"desiredState":"Active"}}'
kubectl get functionrevisions          # the old revision automatically becomes Inactive
```

**Rollback:** set the package version back to the old one (the existing revision is reused)
and – with `Manual` – patch the old revision back to `Active`.
`spec.revisionHistoryLimit` (default 1) controls how many inactive revisions are kept.

**Same pattern for other operators:**
- Argo CD / Flux / Kyverno: Helm release revisions (`helm history`, `helm rollback`)
- Flux itself: `flux install --version=...` or a GitOps-managed `gotk-components.yaml`
- Always check CRD changes before operator upgrades – Helm does **not** update CRDs on
  `upgrade` by default.
