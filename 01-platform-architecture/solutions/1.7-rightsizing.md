# Lösung 1.7 – Right-Sizing

```bash
kubectl -n rightsizing top pod -l app=oversized
# z. B.: oversized-xxx   0m   3Mi   → nginx im Leerlauf braucht fast nichts

# Requests auf Mindestwerte (≈1,2 × Verbrauch, aber min. 10m/16Mi), Memory-Limit = 2 × Request
kubectl -n rightsizing set resources deploy oversized \
  --requests=cpu=10m,memory=16Mi --limits=memory=32Mi

# CPU-Limit entfernen (set resources kann Limits nicht löschen → JSON-Patch)
kubectl -n rightsizing patch deploy oversized --type=json \
  -p='[{"op":"remove","path":"/spec/template/spec/containers/0/resources/limits/cpu"}]'

kubectl -n rightsizing scale deploy oversized --replicas=2
```

**Warum kein CPU-Limit?** CPU ist komprimierbar – Limits führen zu CFS-Throttling und
Latenzspitzen, obwohl der Node freie Kapazität hat. Memory ist nicht komprimierbar, deshalb
bleibt ein Memory-Limit (sonst OOM-Risiko für Nachbarn).

**In der Praxis:** Werte aus Prometheus über einen längeren Zeitraum ableiten, z. B.
```promql
quantile_over_time(0.95, rate(container_cpu_usage_seconds_total{namespace="rightsizing",container="web"}[5m])[7d:5m])
```
oder den Vertical Pod Autoscaler im `Off`-Modus als Empfehlungsgeber nutzen.
