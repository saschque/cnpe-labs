# Solution 4.6 – DORA / deployment metrics

```yaml
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: argocd-metrics
  namespace: argocd
spec:
  selector:
    matchLabels:
      app.kubernetes.io/name: argocd-metrics   # service of the application controller (port 8082)
  endpoints:
    - port: http-metrics
```
> Simpler: Helm values `controller.metrics.enabled=true` and
> `controller.metrics.serviceMonitor.enabled=true`. Check label/port names with
> `kubectl -n argocd get svc --show-labels`.

```promql
# Deployment frequency – successful syncs per app (7 days)
sum by (name) (increase(argocd_app_sync_total{phase="Succeeded"}[7d]))

# Change failure rate (7 days)
sum(increase(argocd_app_sync_total{phase=~"Failed|Error"}[7d]))
  /
sum(increase(argocd_app_sync_total[7d]))

# Apps currently OutOfSync or not Healthy
count(argocd_app_info{sync_status="OutOfSync"})
count(argocd_app_info{health_status!="Healthy"})
```

## The four DORA metrics

| Metric | How to measure it on a GitOps platform |
|--------|----------------------------------------|
| **Deployment frequency** | Successful syncs / Flux reconciliations with a new revision per time period |
| **Lead time for changes** | Time from commit (Git timestamp) to successful sync. Sources: CI pipeline (Tekton annotations) + Argo CD notifications/events with the revision → compute the difference |
| **Change failure rate** | Share of failed syncs, rollbacks (Flagger: `flagger_canary_status` = failed) or deployments that cause an incident |
| **MTTR / failed deployment recovery time** | Time from alert `firing` to `resolved` (Alertmanager webhook) or from a failed sync to the next successful one |

Other platform KPIs: pipeline duration (`tekton_pipelines_controller_pipelinerun_duration_seconds`),
reconcile duration (`gotk_reconcile_duration_seconds` for Flux), resource usage vs. requests
(efficiency), cost per team (OpenCost), developer onboarding time.
