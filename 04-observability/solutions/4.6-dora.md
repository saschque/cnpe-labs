# Lösung 4.6 – DORA-/Deployment-Metriken

```yaml
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: argocd-metrics
  namespace: argocd
spec:
  selector:
    matchLabels:
      app.kubernetes.io/name: argocd-metrics   # Service des Application-Controllers (Port 8082)
  endpoints:
    - port: http-metrics
```
> Einfacher: Helm-Values `controller.metrics.enabled=true` und
> `controller.metrics.serviceMonitor.enabled=true`. Label/Port-Namen mit
> `kubectl -n argocd get svc --show-labels` prüfen.

```promql
# Deployment Frequency – erfolgreiche Syncs pro App (7 Tage)
sum by (name) (increase(argocd_app_sync_total{phase="Succeeded"}[7d]))

# Change Failure Rate (7 Tage)
sum(increase(argocd_app_sync_total{phase=~"Failed|Error"}[7d]))
  /
sum(increase(argocd_app_sync_total[7d]))

# Apps aktuell OutOfSync bzw. nicht Healthy
count(argocd_app_info{sync_status="OutOfSync"})
count(argocd_app_info{health_status!="Healthy"})
```

## Die vier DORA-Metriken

| Metrik | Messung in einer GitOps-Plattform |
|--------|-----------------------------------|
| **Deployment Frequency** | Erfolgreiche Syncs / Flux-Reconciliations mit neuer Revision pro Zeitraum |
| **Lead Time for Changes** | Zeit von Commit (Git-Timestamp) bis Sync erfolgreich. Quelle: CI-Pipeline (Tekton-Annotations) + Argo CD Notifications/Events mit Revision → Differenz berechnen |
| **Change Failure Rate** | Anteil fehlgeschlagener Syncs, Rollbacks (Flagger: `flagger_canary_status` = failed) oder Deployments, die einen Incident auslösen |
| **MTTR / Failed Deployment Recovery Time** | Zeit von Alert `firing` bis `resolved` (Alertmanager-Webhook) oder von fehlgeschlagenem bis nächstem erfolgreichem Sync |

Weitere Plattform-KPIs: Pipeline-Dauer (`tekton_pipelines_controller_pipelinerun_duration_seconds`),
Reconcile-Dauer (`gotk_reconcile_duration_seconds` bei Flux), Ressourcenauslastung vs. Requests
(Effizienz), Kosten pro Team (OpenCost), Developer-Onboarding-Zeit.
