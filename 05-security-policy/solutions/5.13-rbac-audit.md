# Solution 5.13 – RBAC audit

```bash
# 1. All subjects with cluster-admin via ClusterRoleBindings
kubectl get clusterrolebindings -o json | jq -r '
  .items[] | select(.roleRef.kind=="ClusterRole" and .roleRef.name=="cluster-admin")
  | .metadata.name as $b | .subjects[]?
  | "\(.kind) \(if .namespace then .namespace + "/" else "" end)\(.name) (via \($b))"' \
  | tee /tmp/cluster-admins.txt
# Typically: Group system:masters, ServiceAccount ci/legacy-bot (via legacy-bot-admin)

# 2. ServiceAccounts that can read secrets cluster-wide
for ns in ci default; do
  for sa in $(kubectl -n $ns get sa -o jsonpath='{.items[*].metadata.name}'); do
    if [[ $(kubectl auth can-i list secrets -A --as=system:serviceaccount:$ns:$sa) == yes ]]; then
      echo "$ns/$sa"
    fi
  done
done | tee /tmp/secret-readers.txt
# → ci/legacy-bot, default/debugger

# 3. Take away legacy-bot's power
kubectl delete clusterrolebinding legacy-bot-admin
kubectl -n ci create rolebinding legacy-bot-view --clusterrole=view --serviceaccount=ci:legacy-bot
kubectl auth can-i list secrets -A --as=system:serviceaccount:ci:legacy-bot     # no
kubectl auth can-i list pods -n ci --as=system:serviceaccount:ci:legacy-bot     # yes
```

**Watch out during audits:**
- Permissions can also come from **RoleBindings** to ClusterRoles (then only within the namespace).
- Groups: `system:serviceaccounts` / `system:serviceaccounts:<ns>` grant permissions to **all** SAs.
- `view` intentionally does **not** include secrets, `edit`/`admin` do.
- Dangerous verbs besides `*`: `escalate`, `bind`, `impersonate`, `create pods` (→ can use any SA
  in the namespace), `create pods/exec`, `get secrets`.
- Tools: `kubectl auth can-i --list`, plugins like `rbac-tool`, `kubectl-who-can`.
